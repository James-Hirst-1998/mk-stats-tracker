# Experiments

The running log. Every attempt gets a line, including the ones that failed —
knowing which approaches are dead ends is most of what this file is for.
Corrections are appended as new dated lines rather than edited in place, so
the record of being wrong survives.

Started as an item-tracking log, which is why the early entries are all items.

## Open

- **Which shell.** Damage type 2 covers a green shell, a red shell and a fake
  item box alike; the game never tells the victim which it was. The item
  object in the world does know — `+0x04` is the type and `+0x6c` the owner —
  but correlating an object vanishing with a racer being hit is unfinished.
  `analysis/find_item_objects.py` reads the array and learns the type enum;
  what is missing is despawn-to-hit matching. Note the array appeared to hold
  at most 3 live objects at once, which is lower than expected and should be
  checked before building on it.
- **Who threw it.** The collision code passes `r8 = 12`, the "no attacker"
  value, into the damage call, so the victim genuinely does not record it.
  Would have to come from the item object as above.
- **Falling off** has no direct read. "Lost ground with no damage" is a decent
  proxy and is not verified as one.
- **Quantity remaining in a triple.** The held id stays put while all three
  are thrown.
- MEM2 above `0x91800000` has never been captured. Nothing has needed it yet.

## Known Failed / Unstable Approaches
- Block+offset from player block: works in one race, breaks next race due to allocation changes.
- Single/short pointer-chain from position block to held-item byte: not stable; do not retry same chain strategy.
- Scanning MEM1 for pointers to per-race item addresses: no stable pointer path found.
- "Item used" transition matching (old->new): misses held/cart states (for example triple bananas while held), so not reliable.
- Neighbour-pointer scans near `0x809c27f8`: not proven stable across races/restarts.
